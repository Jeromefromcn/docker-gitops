# K3s Phase J — Fine-grained Access Control Design

Date: 2026-08-23

Corresponds to Phase J of the [K3s Service Mesh Capabilities Roadmap](2026-08-19-k3s-mesh-capabilities-roadmap.md): AuthorizationPolicy, restricting the legitimate call relationships between `hello-frontend` → waypoint → `hello-backend` (and each PR lane backend). Deliverable: east-west traffic inside the mesh gets identity-level admission control; illegitimate calls are rejected at the ztunnel/waypoint layer.

Precondition: [Phase I](2026-08-22-k3s-phase-i-traffic-resilience-design.md) is complete and merged into main; the canary weight, timeout, retry, and fault injection for `hello-backend`/`hello-backend-canary` are all carried by `backend-virtualservice.yaml`; PR-lane routing (`lane/httproute.yaml`) keeps its header match and is unaffected. Phase J is fully independent of these routing settings, layering identity-level admission control on top of them without modifying them.

## Scope

**What this phase does:**
- Add two `ServiceAccount`s — `hello-frontend-sa` and `hello-backend-sa` — replacing the `default` ServiceAccount currently shared by all `hello-*` workloads. This is the precondition for workload-level authorization; without a distinguishable identity, `AuthorizationPolicy` cannot express "only frontend can call backend"
- `hello-frontend` (`frontend-deployment.yaml`) mounts `hello-frontend-sa`; `hello-backend` (`backend-deployment.yaml`), `hello-backend-canary` (`backend-canary-deployment.yaml`), and the PR-lane backend template (`lane/deployment.yaml`) all mount `hello-backend-sa` — the three backend variants are treated as the same "role", sharing identity, not distinguished per version
- Two `AuthorizationPolicy`s, both required (reason in "Components and configuration" and "Known limitations" below — this is a key decision revised during design, not an arbitrary belt-and-suspenders):
  - `backend-authorizationpolicy-waypoint.yaml`: uses `targetRefs` to attach to the `waypoint` Gateway resource itself, `action: ALLOW`, only allowing the `hello-frontend-sa` identity — this is the main policy restricting "who can call backend"
  - `backend-authorizationpolicy-require-waypoint.yaml`: uses `selector.matchLabels: {app: hello-backend}` to attach to backend Pods, `action: ALLOW`, only allowing the `waypoint`'s own identity (`cluster.local/ns/pr-lanes/sa/waypoint`) — this is the companion policy preventing waypoint bypass via direct Pod access, and for PR-lane backends without the `use-waypoint` label it is the only line of defense
- Rollout follows an Audit-first rhythm: the main policy attached to the waypoint is first applied with the `istio.io/dry-run: "true"` annotation, observed for one round to confirm no false positives, then the annotation is removed to take effect (details in "Rollout rhythm" below)

**What this phase does NOT do (left to later phases or explicitly excluded):**
- HTTP method/path-level request authorization — only service-level control of "which workload can call which workload". The roadmap itself lists this as a trade-off to refine; here it is finalized as service-level: `hello-backend` currently has only one simple endpoint, method/path granularity has no real defensive benefit, and it would require L7 judgment through the waypoint with policy count growing with instances of PR lanes, making the operational cost disproportionate
- Restricting who can call `hello-frontend` — it is exposed externally via NodePort (`frontend-service.yaml`), a deliberately designed public entry point, outside the authorization scope. **Clarify the actual boundary of this guarantee**: this phase guarantees "workload identity" — only callers carrying the mTLS identity `hello-frontend-sa` can reach `hello-backend`, not "transitive reachability" — anyone can still reach `hello-backend` indirectly via `hello-frontend`'s own `/api` reverse-proxy path, acting as `hello-frontend`, because this phase does not restrict who can call `hello-frontend` itself in the first place. This is not a defect (`hello-frontend` is a deliberately public entry point by design, and this indirect path exposes nothing more than the existing NodePort already does), but future readers should not over-interpret this security guarantee as "only traffic originated by hello-frontend itself — and confined to some source — can reach hello-backend"
- Modifying Phase I's `VirtualService`/`DestinationRule`/`httproute.yaml` — Phase J's `AuthorizationPolicy` is an independent layer stacked on top of existing routing, not touching the routing rules themselves
- Metrics/logs/tracing — Phase K scope
- Rate limiting — Phase L's evaluation scope

## Current-state constraints

Continuing the resource constraint listed in the roadmap itself: `AuthorizationPolicy` and `ServiceAccount` are pure control-plane resources, consuming none of `pr-lanes-quota`'s CPU/memory, and do not affect the 7 PR-lane concurrency capacity calculated in Phase I.

Continuing the roadmap's explicit requirement for Phase J: misconfiguring the authorization policy (especially accidentally switching to deny-by-default) would cut all east-west traffic inside `pr-lanes` at once, replaying the same class of pitfall as the [2026-08-19 NPM NodePort incident](../../incidents/2026-08-19-npm-to-k3s-nodeport-outage.md) — this phase's verification steps must include an observation period, not going straight to production mode.

## Architecture

```mermaid
flowchart LR
    fe["hello-frontend\n(SA: hello-frontend-sa)"] -->|"mTLS identity:\nhello-frontend-sa"| waypoint["waypoint\n(SA: waypoint, existing)"]
    deny1["Other callers"]
    deny2["Direct-connect sources\n(e.g. a stray debug pod)"]

    waypoint --> authz1{"Policy 1 (attached to Gateway/waypoint)\nFrom hello-frontend-sa?"}
    authz1 -.->|No, deny| deny1

    authz1 -->|Yes, forward per Phase I routing rules| authz2{"Policy 2 (attached to each backend Pod,\nselector app=hello-backend)\nFrom waypoint SA?"}
    authz2 -.->|No, deny (including attempts to bypass\nwaypoint and connect directly to Pod)| deny2

    authz2 -->|Yes| stable["hello-backend\n(lane: baseline)"]
    authz2 -->|Yes| canary["hello-backend-canary\n(lane: canary)"]
    authz2 -->|Yes| prlane["hello-backend-pr-N\n(lane: pr-N)"]

    style deny1 fill:#fee,stroke:#c00
    style deny2 fill:#fee,stroke:#c00
```

Policy 1 evaluates at the waypoint hop "whether the original caller is `hello-frontend-sa`" — this hop can see the true identity, because the waypoint is where traffic first enters a mesh enforcement point. Policy 2 evaluates at each backend Pod's own ztunnel "whether this connection comes from the waypoint" — this hop cannot see the original caller's identity (official docs confirm: when the waypoint forwards downstream, the destination ztunnel sees the waypoint's own identity; see "Known limitations"), so it can and only needs to check "is it from the waypoint". The two layers together equal "only calls from `hello-frontend` authorized via the waypoint can reach backend". All three backend variants mount the same `hello-backend-sa` (needed by Policy 1's judgment), and all are selected by the same Policy 2's `selector.matchLabels: {app: hello-backend}` — no authorization resource needs to be modified or added when a new PR lane is created; the `kustomize` template applies `serviceAccountName` and automatically inherits both layers of protection.

## Components and configuration

| Item | Decision | Rationale |
|---|---|---|
| ServiceAccount granularity | Two: `hello-frontend-sa` (frontend-only), `hello-backend-sa` (shared by baseline/canary/all PR lanes) | Currently all workloads share the `default` SA, so mTLS identity cannot distinguish callers. `source.namespaces` cannot distinguish because frontend/backend are both in `pr-lanes`; IP-based rules break after Pod recreation and are unreliable. The three backend variants share one identity because they are the same "role" — Phase J's authorization semantics are "can frontend call the backend role", not per-version distinction |
| Authorization granularity | Service-level (workload-to-workload), without HTTP method/path | See the "Scope" section above; the roadmap's trade-off-to-refine is finalized here |
| Why two `AuthorizationPolicy`s, not one | Official docs confirm ([istio.io](https://istio.io/latest/docs/tasks/security/authorization/authz-waypoint/), [ambientmesh.io](https://ambientmesh.io/docs/security/waypoint-authz/)): when the waypoint forwards traffic to a downstream Service, if that Service lacks the `use-waypoint` label, the destination ztunnel sees the source identity as the waypoint itself, not the original caller. `hello-backend-pr-N` is exactly this case (its Service has no `use-waypoint`, traffic is forwarded through `hello-backend`'s waypoint). A single `AuthorizationPolicy` attached to backend Pods checking `hello-frontend-sa` would always see the waypoint identity on the PR-lane path and would wrongly block all legitimate traffic — this is precisely the risk the original design (in an earlier version of this document) marked as "to be verified"; verification confirmed it would fail, see "Known limitations" | See the two rows below |
| Policy 1 (main policy) | `targetRefs` pointing to `kind: Gateway, group: gateway.networking.k8s.io, name: waypoint`, `action: ALLOW`, `rules[].from.source.principals: ["cluster.local/ns/pr-lanes/sa/hello-frontend-sa"]` | Attached to the waypoint itself rather than individual backends, evaluated at the hop where traffic first enters a mesh enforcement point (waypoint). Here the original caller's true identity is visible, unaffected by the identity-masking of "forwarding downstream". The same waypoint carries baseline/canary/all-PR-lanes routing (Phase I architecture), so attaching here naturally covers all downstream targets without enumerating them one by one |
| Policy 2 (companion policy, enforcing that traffic must pass through the waypoint) | `selector.matchLabels: {app: hello-backend}`, `action: ALLOW`, `rules[].from.source.principals: ["cluster.local/ns/pr-lanes/sa/waypoint"]` | Only allows traffic from the waypoint's own identity to reach backend Pods, blocking any attempt to bypass the waypoint and directly hit a Pod IP or a Service without the waypoint label. Defense in depth beyond Policy 1 for baseline/canary; for PR-lane backends (whose Service itself lacks `use-waypoint`) it is the only line of defense — without this policy, directly calling `hello-backend-pr-N.pr-lanes.svc.cluster.local`, bypassing `hello-backend`, is completely outside Policy 1's control |
| Not worried about kubelet liveness/readiness probes being blocked by Policy 2 | Verified and ruled out: ambient has a dedicated exemption for kubelet probe traffic — probe packets are SNAT'd to a fixed link-local address (`169.254.7.127`), and ztunnel recognizes this address and passes it straight through, bypassing `AuthorizationPolicy` identity checks entirely; this is a built-in design of the ambient architecture, so Phase J needs no special handling for it | This is a risk proactively verified and ruled out before implementation, not an accident discovered post-rollout |
| Rollout mechanism | Policy 1 (carried by waypoint/Envoy) is first applied with the `istio.io/dry-run: "true"` annotation for observation, then the annotation removed once no false positives are confirmed; Policy 2 (carried by ztunnel) goes straight to manual comparison, no dry-run | Policy 1 attaches to the waypoint (full Envoy), which natively supports dry-run shadow mode. Policy 2's dry-run is a new ztunnel feature added in Istio 1.29, requiring an extra cluster-level feature flag on istiod (`AMBIENT_ENABLE_DRY_RUN_AUTHORIZATION_POLICY=true`) to enable, beyond the scope of "only changing pr-lanes app-layer resources" — not worth touching istiod's cluster-level setting for this one policy; Policy 2's behavior is also simple and predictable (under the current architecture only the waypoint directly connects to these Pods), so manual comparison suffices |

## Repo layout

```
vps_oracle/k3s/apps/hello/k8s/
  frontend-serviceaccount.yaml               # new: hello-frontend-sa
  backend-serviceaccount.yaml                # new: hello-backend-sa
  backend-authorizationpolicy-waypoint.yaml  # new: Policy 1, targetRefs Gateway/waypoint, ALLOW from hello-frontend-sa
  backend-authorizationpolicy-require-waypoint.yaml
                                              # new: Policy 2, selector app=hello-backend, ALLOW from waypoint SA
  frontend-deployment.yaml         # modified: add spec.template.spec.serviceAccountName: hello-frontend-sa
  backend-deployment.yaml          # modified: add serviceAccountName: hello-backend-sa
  backend-canary-deployment.yaml   # modified: add serviceAccountName: hello-backend-sa

vps_oracle/k3s/apps/hello/lane/
  deployment.yaml                  # modified: add serviceAccountName: hello-backend-sa
                                    # (template change; every future dynamically created PR lane
                                    #  inherits it automatically, no need to change
                                    #  pr-lanes-appset.yaml's patch list)
```

Everything lands in the existing `k8s/` and `lane/` directories, following existing naming conventions. New files under `k8s/` are picked up automatically by ArgoCD's existing `hello` Application; no new Application or Kustomization entry is needed. `lane/kustomization.yaml` currently lists only three resources — `deployment.yaml`/`service.yaml`/`httproute.yaml` — no new entry needed; it is only editing the content of the existing `deployment.yaml`.

A new hidden dependency worth noting: `lane/deployment.yaml` is rendered by a different ArgoCD Application (the `pr-lanes` ApplicationSet, not the same as the `hello` Application that creates `hello-backend-sa`), and now references `hello-backend-sa`, which only the `hello` Application creates. If `hello-backend-sa` is ever accidentally deleted, or the `hello` Application's sync breaks, newly opened PR-lane Pods will fail to schedule because the ServiceAccount is not found — but the error message is Kubernetes's common serviceaccount-lookup failure and won't obviously point to "mesh authorization", making debugging easy to go down the wrong path. Low probability but currently undocumented; flagging it here suffices.

## Rollout rhythm

1. First merge all of this phase's YAML (two `ServiceAccount`s, Policy 2, the `serviceAccountName` fields in the four Deployments, and Policy 1 with the `istio.io/dry-run: "true"` annotation) — Policy 2 taking effect immediately without an observation period is deliberate, see the reason below
2. After Policy 2 takes effect, do a manual comparison: review the current architecture ([Phase F+G](2026-08-18-k3s-phase-fg-mesh-pr-lanes-design.md) / Phase I design) to confirm there is presently no legitimate path for any non-waypoint direct connection to backend Pods, then use a smoke test on baseline/canary/(any open PR lane) to confirm normal traffic is unaffected
3. Policy 1 observation period: check the waypoint's log or the `istio_dry_run_allow`/`istio_dry_run_deny` metrics, confirming:
   - all current legitimate traffic reaching `hello-backend`/`hello-backend-canary`/`hello-backend-pr-N` (from `hello-frontend`) lands in `dry_run_allow`
   - no unexpected `dry_run_deny`
4. If the dry-run annotation produces no records on this waypoint (judged unsupported): downgrade to manual comparison — inspect the waypoint access log / run a smoke test directly, manually confirming that the only current caller of the `hello-backend` series is `hello-frontend`, without relying on dry-run records
5. Once the observation period shows no anomalies, remove Policy 1's `istio.io/dry-run` annotation to take effect (Enforce)
6. As in Phase E: the Audit→Enforce switch is a manual judgment, not an automated timed switch

Why Policy 2 does not go through a dry-run observation period like Policy 1: its judgment condition is extremely simple (whether the source is the waypoint's identity), and under the current architecture (before Policy 2 takes effect) only the waypoint ever establishes connections to backend Pods — no other component has ever, or is designed to, connect directly to these Pods. A manual comparison that "the current state is indeed this" confirms the same thing an automated observation period would, without reducing certainty by skipping the observation period.

## Verification checklist (phase J pass criteria; the implement stage will refine into step-by-step)

**Pre-rollout:**
1. `kubectl -n pr-lanes get application hello` → `Synced` + `Healthy`
2. Both `ServiceAccount`s are created, and the Pods of the three backend Deployments and the frontend Deployment all mount the corresponding SA (`kubectl get pod -o jsonpath='{.spec.serviceAccountName}'`)

**After Policy 2 takes effect (manual comparison, see rollout rhythm):**
3. Normal requests through `hello-frontend` (including those with the `x-pr-lane` header hitting the corresponding lane, and canary weight split hitting canary) have unaffected latency/success rate
4. kubelet's liveness/readiness probes on the three backend variants keep working (`kubectl get pods -l app=hello-backend` shows no unexpected increase in `Restarts`), verifying that the kubelet probe exemption ruled out in "Known limitations" actually works on this cluster

**Policy 1 dry-run observation period:**
5. Normal requests through `hello-frontend` are all `allow` in the dry-run records, with no unexpected `deny`
6. If any PR lane is open right now, specifically confirm its dry-run records are also `allow`

**After Policy 1 switches to Enforce:**
7. Normal requests (same paths as items 3 and 5) have latency/success rate unchanged from before Phase J
8. Use a source lacking the `hello-frontend-sa` identity (e.g. a temporary debug pod using the `default` SA) to call the Service hostnames of `hello-backend`/`hello-backend-canary` — since these two Services themselves have the `use-waypoint` label, ztunnel automatically routes the request to the waypoint, which is Policy 1's verification path; confirm it is rejected (`PERMISSION_DENIED` or connection refused)
9. **Waypoint-bypass direct-connect test**, verifying that Policy 2's layer of defense takes effect independently and does not depend on Policy 1:
   - For `hello-backend`/`hello-backend-canary`: the Service hostname itself is routed to the waypoint (see item 8), so to test true bypass it must directly hit the **Pod IP** (`kubectl -n pr-lanes get pod -o wide` to get the IP, directly curl `http://<pod-ip>:8080/`), skipping the Service-level waypoint routing mechanism
   - If any PR lane is open right now: `hello-backend-pr-N`'s Service itself lacks the `use-waypoint` label, so directly curling its Service hostname (no Pod IP needed) is already the true bypass path
   - Both cases should be rejected
10. If any PR lane is open right now, re-run the corresponding normal-traffic path from item 6, confirming it still passes after Enforce
11. `kubectl describe resourcequota pr-lanes-quota -n pr-lanes` confirms the new resources consume no quota (expected no change; `ServiceAccount`/`AuthorizationPolicy` are not counted)
12. Re-check all existing Applications still `Synced` + `Healthy`

## Known limitations / risks to verify

- **When the waypoint forwards to a downstream Service without the `use-waypoint` label, the identity is masked — verified and already corrected in the design**: the original design used only one `AuthorizationPolicy` attached to backend Pods checking `hello-frontend-sa`, which an earlier version of this document listed as a "risk to verify". Verification result ([istio.io](https://istio.io/latest/docs/tasks/security/authorization/authz-waypoint/), [ambientmesh.io/docs/security/ztunnel-authz](https://ambientmesh.io/docs/security/ztunnel-authz/)): it does fail — "when the waypoint forwards to a downstream without the waypoint label, the destination ztunnel sees the waypoint's own identity" is established ambient behavior, not an anomaly specific to this cluster; the PR-lane Service `hello-backend-pr-N`, lacking the `use-waypoint` label, is squarely in this case. The correction the official docs give is exactly the two-policy design this document now adopts (Policy 1 attached to Gateway/waypoint checking the original identity, Policy 2 attached to Pod checking whether it comes from the waypoint); this is now a finalized part of the document, no longer a to-be-verified item
- **The `istio.io/dry-run` annotation is natively supported on the waypoint (full Envoy), but on ztunnel it is a new Istio 1.29+ feature requiring an extra istiod cluster-level feature flag — this was verified live during Task 3's Policy 1 rollout and is no longer a to-be-verified item**: after Policy 1 went live with `istio.io/dry-run: "true"`, the correct signal to observe is **not** the waypoint log grep this document originally envisioned (`kubectl logs deploy/waypoint | grep dry.run` produced no output in testing), but the `rbac.istio_dry_run_allow_.shadow_denied` counter in the Envoy admin stats endpoint (`pilot-agent request GET stats`) — during the observation period it incremented precisely in step with the test traffic generated (1 after 1 call, 21 after 20 more calls), while the real `rbac.allowed`/`rbac.denied` stayed at 0 throughout, confirming no real interception happened during dry-run. This confirms that "dry-run is natively supported on waypoint's full Envoy" truly holds on this cluster, and gives a concrete, reproducible observation method, replacing the original rollout-rhythm step 4 fallback of "downgrade to manual comparison if nothing is output" — the fallback was never triggered. Additionally, while Policy 1 was alive, `status.conditions` showed `type: ZtunnelAccepted, status: "False", reason: UnsupportedValue`, with a message mentioning "ztunnel does not support dry-run" — this is a misleading red herring, because Policy 1 uses `targetRefs` to attach to the `waypoint` Gateway, going through the waypoint's Envoy RBAC filter (L7), never touching ztunnel; this status field describes ztunnel (relevant to pod-selector policies like Policy 2), not Policy 1's actual execution path. But it also surfaces a real observability gap: on this Istio version, for policies attached to a Gateway via `targetRefs`, no CRD status field can give a positive signal that "the waypoint has accepted this policy" — `ZtunnelAccepted` describes a different path, and there is no `WaypointAccepted` or equivalent field. The only way to confirm is behavioral observation — Envoy admin stats, istiod's ADS push log, and actual traffic testing — all three requiring manual execution, not a glance at `kubectl get authorizationpolicy` status. When debugging waypoint-targeted policies in the future, skip `status.conditions` directly and use these three methods instead
- **Honest addition: the observation window above never actually observed a single request with a legitimate identity being shadow-allowed; the Audit-first discipline was not fully upheld in this implementation**: throughout the dry-run observation period, the increments of `rbac.istio_dry_run_allow_.shadow_denied` all came from deliberately sent debug-pod calls lacking the `hello-frontend-sa` identity; the corresponding `rbac.istio_dry_run_allow_.shadow_allowed` counter stayed at `0` throughout — meaning the dry-run window itself never observed a single request carrying the legitimate `hello-frontend-sa` identity being shadow-allowed. Real frontend traffic success (`200`) was first confirmed only after Task 4 switched Policy 1 to Enforce (see the Task 4/5 traffic tests above), not during the dry-run observation window. Theoretically "confirm legitimate traffic will be shadow-allowed first, then switch to Enforce" is the complete Audit-first verification, but in practice the legitimate path was first confirmed working only after switching to Enforce — a real verification gap exists in between. Mitigating context: `pr-lanes` is a lab-namespace demo app for validation with no real user traffic; if the switch went wrong, rollback is a single `git revert` fixing it in one commit; and in practice the legitimate path (`hello-frontend` → `hello-backend`) was confirmed working within minutes after switching to Enforce, so the exposure window was short
- **Beyond the stats counter, there is a more direct way to judge whether an `AuthorizationPolicy` attached to a Gateway is currently in dry-run or actually enforcing, without needing traffic first**: `kubectl -n pr-lanes exec deploy/waypoint -- pilot-agent request GET config_dump` — if the policy's rules appear in the RBAC filter's `rules` block, it is enforcing; if in the `shadow_rules` block, it is still dry-run. This method directly reads the waypoint's own proxy config and answers "what mode is this policy in right now", unlike the stats-counter method above, which only shows numbers after test traffic has come in. The two methods are complementary: config_dump suits "don't want to wait for traffic, confirm the current mode immediately", stats counter suits "traffic already present, confirm the actual allow/deny distribution"
- **`status.conditions` remains stuck on the dry-run-era old message after removing the `istio.io/dry-run` annotation and switching to Enforce — verified as a permanent display defect, not a transient sync lag**: after Task 4 removed the annotation (changing only `metadata.annotations`, not `spec`), `status.conditions[0]` kept showing the previous `UnsupportedValue` / dry-run message, with `observedGeneration` stuck at `"1"`; the reason is that an annotation-only edit does not advance the Kubernetes object's `metadata.generation`, and Istio's write logic for this status field appears to trigger on generation — no generation change, no status recomputation. An independent re-check more than ~20 minutes after Task 4 completed still showed `status.conditions` verbatim identical — ruling out "sync just hasn't caught up", and this field most likely won't clear on its own without a spec-level change. Actual enforcement has already been confirmed via behavioral evidence: the istiod ADS push log (`Push debounce stable ... for config AuthorizationPolicy/pr-lanes/hello-backend-waypoint-frontend-only`) confirms the config was indeed re-pushed to the data plane; the Task 4/5 traffic tests (illegitimate identity receives `403`, real `hello-frontend-sa` identity receives `200`) confirm the rule is indeed in effect. When debugging this policy in the future, don't wait for this status field to clean up — it very likely never will, unless the object later gets a spec-level change advancing the generation; look at the behavioral evidence directly
- **kubelet health checks on backend Pods are verified unaffected by Policy 2**: ambient's exemption mechanism for kubelet probe traffic (SNAT to a fixed link-local address) resolves this concern at the architecture level, but it remains in checklist item 4 to confirm via the actual `Restarts` count that behavior on this cluster matches the documentation, not relying on the documentation alone
- **`hello-backend-sa` is a single identity shared by all three backend variants, so these two `AuthorizationPolicy`s cannot express finer restrictions like "only allow calling baseline, not canary"**: not needed now — Phase J's authorization semantics are "can frontend call the backend role", not version-level access control. If version-level restriction is needed later, the ServiceAccount must be re-split, which is a later-phase scope
- **Policy 1 is attached to the shared `waypoint` Gateway resource, so if other Services start using the same waypoint in the future (currently only the hello-backend series uses it), they would automatically fall under the "only allow hello-frontend-sa" restriction**: this is a deliberately accepted coupling, not an oversight — currently `pr-lanes` has only one shared waypoint, and the roadmap's current-state constraints include no other service planned to join this waypoint. If a future service shares this waypoint but needs different caller restrictions, it will need multiple waypoints or a redesign of Policy 1's `targetRefs` scope, which is future work beyond this phase
- **Policy 2's protection of PR-lane backends (`hello-backend-pr-N`) was never actually tested against a real, existing PR lane during this whole implementation (three opportunity points in Task 2, Task 4, Task 5)**: at all three checks, `kubectl -n argocd get applications | grep hello-pr` returned empty — no `hello-pr-*` Application exists. As stated in the "Repo layout" and "Policy 2" rows, `hello-backend-pr-N`'s Service has no `use-waypoint` label, so Policy 2 is its only line of defense; this line is currently supported only indirectly — via architecture analysis (selector `app: hello-backend` covering all backend variants, PR-lane templates inherently inheriting this label) and via Policy 2's generic-mechanism verification against baseline/canary (Task 2, Task 4, Task 5 all confirmed Policy 2 correctly blocks direct-connect-to-Pod-IP bypass attempts) — never actually verified against a real `hello-backend-pr-N` target that directly curling its Service hostname (no Pod IP needed, since it has no waypoint routing anyway) would be blocked. The next time a real PR lane opens, this test should be added — corresponding to checklist items 6, 9, and 10 — to confirm the theoretical derivation matches actual behavior

## Handoff to later phases

Phase K (observability integration) will point `pr-lanes`'s metrics/logs/tracing to `lab-environment`. This path is `lab-environment` actively scraping/pulling the existing Prometheus endpoints of istiod/ztunnel/waypoint inside `pr-lanes`, which does not involve calling the `hello-frontend`/`hello-backend` application-layer endpoints, and will not be affected by the `AuthorizationPolicy`s added this phase (`selector` only matches `app: hello-backend`) — Phase K's design should still re-confirm this assumption and not presume the two can't conflict.

If Phase L takes the `EnvoyFilter` path for rate limiting, `EnvoyFilter` and this phase's `AuthorizationPolicy` both stack config on the waypoint's Envoy; theoretically independent filter chains won't conflict, but Phase L's evaluation should factor in that "Phase J already runs an RBAC filter on the waypoint".
