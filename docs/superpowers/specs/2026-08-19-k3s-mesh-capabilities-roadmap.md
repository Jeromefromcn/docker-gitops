# K3s Service Mesh Capability Completion Roadmap

Date: 2026-08-19

## Background

The [F+G phase](2026-08-18-k3s-phase-fg-mesh-pr-lanes-design.md) installed Istio Ambient (istiod + ztunnel + istio-cni + waypoint) + Gateway API in the `pr-lanes` namespace, with the deliverable deliberately narrowed to a single "PR preview lane" scenario: only header-based two-version routing was done, without touching the rest of the service mesh's standard capabilities — canary weights, timeout/retry, fine-grained authorization, observability integration, circuit breaking, and rate limiting.

After [deployment-topology v3](../../deployment-topology/v3.md) was finalized, the current state was inventoried item-by-item against the industry's four service-mesh capability classes (traffic management, security, observability, resilience), landing in three categories:

- **Already present**: mTLS mutual auth, health checks, header-split gray release, canary weight routing (90/10), timeout/retry, circuit breaking (outlier detection), fault injection — ztunnel/waypoint/HTTPRoute are already running, and phase I (2026-08-22) further completed weights/timeout/retry/circuit-breaking/fault-injection (see the I implementation result below)
- **Not configured**: fine-grained access control (AuthorizationPolicy), metrics integration, log collection — the components already run in the cluster, it's purely that the corresponding YAML was never written
- **Not present**: distributed tracing, rate limiting — no corresponding resources currently, and rate limiting additionally involves the Gateway API channel choice

This doc converges the "not configured" and "not present" categories into a roadmap, continuing the next batch of phases after F+G. The scope **covers only the `pr-lanes` namespace** — `lab-environment` isn't in the mesh, and the other business services migrated back to compose on 8/18 and are unaffected by this roadmap.

## Goals

- **Prefer reusing already-running components** for the capabilities being completed — don't reinstall a whole stack just to add one capability; F+G already pushed the budget near its ceiling, so this constraint is tighter than it was during F+G
- Anything achievable with pure YAML/CRD config adds no Deployment; when a new component is genuinely needed, prefer hooking into `lab-environment`'s existing Prometheus/Loki/Jaeger rather than standing up a separate one in `pr-lanes`
- Security-sensitive changes (authorization policy) go through their own spec → plan → implement → verify cycle, not mixed into the same deliverable as low-risk traffic-governance config — following the precedent of E's supply chain security being independent of D's service migration
- Honest assessment: capabilities confirmed as not worthwhile or not mature (rate limiting) are explicitly marked "evaluated, may not do", and not forced just to make the list look complete

## Current-state constraints

- **Resources are tighter than during F+G**: live `free -h` measurement (2026-08-19) — 23Gi total, only 813Mi truly free, `available` 6.2Gi (including reclaimable cache), 4Gi swap with 3.4Gi used (85%). This is tighter than the "about 6.4Gi available" recorded in the [2026-08-05 roadmap](2026-08-05-k3s-cloud-native-platform-roadmap.md), and the swap usage itself is a signal to watch — any phase of this roadmap that observes OOMKilled or swap continuing to climb should pause the evaluation first, not push ahead with installation
- **`pr-lanes-quota` is already very tight**: `requests.cpu: 400m / requests.memory: 768Mi`, `limits.cpu: 1200m / limits.memory: 1536Mi` ([resourcequota.yaml](../../../vps_oracle/k3s/apps/hello/k8s/resourcequota.yaml)). istiod-values.yaml already recorded one lesson of "the waypoint's default resource requests alone blow this quota", so any resource added by this roadmap must first be confirmed not to collide with this ceiling, especially capabilities like circuit breaking/rate limiting that need extra sidecar or filter overhead
- **Gateway API is installed on the standard channel** ([standard-install.yaml](../../../vps_oracle/k3s/gateway-api/standard-install.yaml)), without the experimental feature channel — **the original note about "native rate limiting (GEP-2257)" is wrong**: GEP-2257 is actually the Duration string format standard, unrelated to rate limiting; the Gateway API official GEP list has no rate limiting API to this day, nor does the experimental channel. This invalidates the "upgrade to experimental for native rate limiting" path, and Phase L ultimately adopted `TrafficExtension` + Lua (see the L phase design doc)
- **`lab-environment` is not in the mesh**: Prometheus/Loki/Jaeger all live in `lab-environment`, so `pr-lanes` connecting to them means cross-namespace traffic — the same class of risk as the two gotchas hit in the last two days (the NPM→NodePort black-hole incident and the Cilium socket-LB narrowing cascade): network-layer config seems independent but is actually mutually coupled. Before Phase K starts, it must first confirm whether Cilium NetworkPolicy allows this cross-namespace path; can't assume "same cluster means interconnectivity by default"

## Per-phase design notes

### Phase I: why four capabilities merge into one phase

Canary weights, timeout/retry, circuit breaking, and fault injection have different semantics but are highly homogeneous in implementation: all are "CRDs istiod/waypoint already read, add one YAML and it takes effect", involving no new components and mutually independent risk (changing circuit-breaking config doesn't affect timeout/retry). **The sole resource-budget exception is canary weights themselves** — Gateway API's weight splitting spans Services rather than subsets, so having a real second version requires a new `hello-backend-canary` Deployment, after which `pr-lanes-quota` rose from `400m/512Mi` to `500m/640Mi`, and lane capacity dropped from 8 to 7 (this trade-off is recorded in the implementation plan's Global Constraints, an accepted cost). Unlike F+G, which had to merge because "namespace-per-PR model vs waypoint-centralized model" fought each other, this is purely an efficiency judgment: "same-kind work doesn't need four separate spec → plan → implement → verify cycles".

Canary weights (originally designed via HTTPRoute `backendRefs[].weight`) and the existing header routing ([lane/httproute.yaml](../../../vps_oracle/k3s/apps/hello/lane/httproute.yaml)) share the same Gateway/waypoint and don't conflict: header match takes precedence over weight splitting (Gateway API merge rules were always match-count-first), so they can coexist — PR lanes keep using header-based precise routing, and baseline traffic additionally splits a portion for canary validation of a new version, without interfering.

> **I implementation correction**: during implementation, canary weights ultimately moved to `VirtualService` (with `backend-httproute.yaml` deleted for conflicting with `VirtualService` on the same host, see the I implementation result below), not HTTPRoute. But the "doesn't interfere with existing header routing" conclusion still holds — `lane/httproute.yaml`'s PR lane header match was untouched, and implementation verification confirmed its precedence is unaffected.

Fault injection needs Istio's `VirtualService` (not a Gateway API core resource), but the `VirtualService` CRD already exists from the istio-base install, so no extra component is needed — it belongs in this phase rather than a separate "not present" phase because, like circuit breaking/timeout-retry, it's just "CRD already there but no resource written".

#### Phase I implementation result(2026-08-22 done, merged to main and verified online)

Phase I is done and merged to `main`; the implementation produced two deviations from the original design that were written back into the design doc, recorded here at the roadmap level:

- **Canary weights now carried by `VirtualService`, `backend-httproute.yaml` deleted**. The original design expected `HTTPRoute.backendRefs[].weight` (Gateway API) to manage weight splitting and `VirtualService` to manage only fault injection, coexisting. During implementation (Task 3) the two turned out **unable to coexist on the same host**: `HTTPRoute`'s rule has no header-match condition, making it an "unconditional" rule, and when Istio merges Gateway API and traditional API rules into the waypoint's single Envoy route table, such an unconditional rule overwrites the `VirtualService` rule on the same host entirely, so the fault-injection header match was never evaluated by Envoy. The final disposition was to delete the whole `backend-httproute.yaml`, making `VirtualService` the sole routing-config source for the `hello-backend` host, single-handedly carrying the four functions: canary weight (90/10), timeout (10s), retries (2 times), and fault injection (`x-fault-test: delay`/`abort`).
- **Fault injection's `fault.delay` and the same rule's `timeout` don't stack**. Measured `x-fault-test: delay` (`fixedDelay: 15s`) combined with the same rule's `timeout: 10s`: the request ran the full ~15s and returned `200`, not truncated by the timeout — presumably the route timeout timer only starts when the router filter begins processing the upstream request, later than the fault filter's decode-time delay. This is an Istio behavior limitation, not a config error; verifying timeout's effect on real slow requests can't be done via fault injection, deferred to a later phase.
- **Circuit breaking (outlier detection) was pushed to the Envoy dataplane** (`consecutive5xxErrors: 3, interval: 30s, baseEjectionTime: 30s, maxEjectionPercent: 100`, with `maxEjectionPercent: 100` changed because both backends are `replicas: 1`, and 50% would unconditionally floor to 0 ejectable endpoints). But **behavioral ejection couldn't be triggered via fault injection** — `x-fault-test: abort` is an Envoy local reply, never dispatched to the upstream cluster, so outlier detection's `consecutive5xxErrors` never sees it. Genuinely verifying ejection requires the upstream to actually receive requests and return 5xx (change the app or break the pod), beyond this phase's CRD-only scope, deferred to a later phase.

Full details in the [I phase design doc](2026-08-22-k3s-phase-i-traffic-resilience-design.md)'s "Known limitations / failure modes".

### Phase J: why the authorization policy is independent of phase I

AuthorizationPolicy misconfiguration has a failure mode totally different from I's four items — I's misconfig at worst sets an unreasonable timeout or a wrong canary ratio, the service stays reachable; the authorization policy misconfigured (especially accidentally cut to deny-by-default) directly blocks all east-west traffic inside `pr-lanes`, replaying the "new setting takes effect inside the cluster while external consumers silently disconnect" accident pattern ([2026-08-19 NPM NodePort incident](../../incidents/2026-08-19-npm-to-k3s-nodeport-outage.md) is the same kind of gotcha: one line of Cilium socketLB config change, with a blast radius far larger than expected). Following E's precedent of supply chain security being independent of D's migration, the authorization policy needs its own spec → plan → implement → verify cycle, and the verification step must include "observe a round in Audit/dry-run mode first, confirm legal traffic isn't wrongly killed, then switch to Enforce" — the same path Kyverno took from Audit to Enforce, don't repeat the risk of going straight to production mode.

### Phase K: why "reuse lab-environment" was overturned, in favor of a separate namespace + compose's existing monitoring

This section's original text argued for reusing `lab-environment`'s existing Prometheus/Loki/Jaeger on the grounds that its resource quota is roomier than `pr-lanes-quota`. That reasoning didn't hold up during verification before Phase K started, so the original text was overturned; the full process is in the [K phase design doc](2026-08-24-k3s-phase-k-observability-design.md), summarized here into two key findings:

1. **`lab-environment`'s monitoring isn't actually running day-to-day**: all its Deployments (including Prometheus/Loki/Jaeger/Grafana/Promtail) default to `replicas: 0`, so it's not "available" infrastructure; reusing it means `pr-lanes` observability is off by default, only turning on when a human brings up the whole `lab-environment` stack for SRE practice.
2. **`lab-environment/README.md` explicitly declares this monitoring to be deliberately isolated from `vps_oracle`'s real monitoring** ("no shared Prometheus/Grafana/alerting … deliberate — this stack's `toxiproxy`-driven chaos testing shouldn't share a pipeline with real incident alerting"). The original design attached `pr-lanes` (real mesh traffic) observability to this chaos-test environment that "deliberately doesn't share a pipeline with real monitoring" — the direction itself violates this existing boundary, not a mere resource trade-off.

Phase K's new design adopted two decisions: `lab-environment` stays untouched (its own SRE practice still needs its own monitoring, unaffected by this roadmap); `pr-lanes` metrics/logs/tracing point instead at compose's existing Prometheus/Grafana, and the missing Loki/Jaeger go into a newly created `mesh-observability` namespace independent of both `pr-lanes-quota` and `lab-environment`. The network direction was also corrected: during Phase K design it was found that "pod actively connects out to the docker compose network" is blocked dead by Cilium/istio-cni's existing traffic-redirection mechanism (a cluster-level existing limitation, not introduced by this phase); the new design changed all three telemetry flows to "compose's existing Prometheus/Grafana actively connecting to k3s NodePort" — the only cross-docker/k3s direction already run in production and verified safe on this machine.

### Phase L: why rate limiting is only an "evaluation", not a "promised delivery"

Rate limiting has two implementation paths, both with obvious costs:

- **Upgrade Gateway API to the experimental channel**: replaces the current standard-channel install, gaining a batch of experimental CRDs currently unused, and the experimental API itself is still changing, raising compatibility risk at future K8s/Gateway API version upgrades
- **Istio EnvoyFilter**: functionally feasible (istiod already there), but `EnvoyFilter` is the escape hatch that directly rewrites Envoy's low-level config; the official docs themselves warn it's tightly coupled to Istio versions and easily breaks when upgrading Istio, with far higher maintenance cost than the rest of this roadmap

And `pr-lanes` is currently just a demo namespace validating the PR preview lane mechanism — no real user traffic, and no actual abuse or overload risk yet, so the problem rate limiting solves doesn't exist yet. The [README](../../../vps_oracle/k3s/README.md) also mentions the future plan is "batch-onboarding `workloads`-shaped services once `pr-lanes` stabilizes", at which point there'd be real traffic worth rate-limit protection. This phase's output is a trade-off record for decision reference at that point, not a promised implementation in this roadmap.

#### Phase L implementation result(2026-08-25 done)

After the evaluation phase ended, both of the original two paths were disproved by verification, and a third path was ultimately adopted. Full trade-offs and verification are in the [L phase design doc](2026-08-25-k3s-phase-l-ratelimit-design.md), summarized here:

- **Both original paths are dead ends**: upgrading Gateway API to the experimental channel — verification confirmed the official GEP list has no rate limiting API to this day, nor does the experimental channel, so the upgrade gains no native rate limiting; Istio `EnvoyFilter` — functionally feasible, but not officially blessed under ambient mode (waypoint is the dataplane introduced only in Istio 1.30, and `EnvoyFilter`'s ambient compatibility has no official guarantee).
- **Adopted `TrafficExtension` + Lua fixed-window token bucket**: Istio 1.30's `TrafficExtension` CRD mounts an inline Lua filter on the `pr-lanes` waypoint, `hello-backend` rate-limited to 60 req/min, over-limit returns 429, no new components.
- **Online verification(2026-08-25)**: a 100-request burst measured 59×200 / 41×429, close to the 60 req/60s design target (the difference comes from fixed-window boundary jitter with sequential requests); 429 responses carry the `x-envoy-ratelimited: true` header and body "rate limit exceeded"; after waiting 65+ seconds requests returned to 200, confirming the window reset works.
- **filter chain order: an earlier record was wrong, now corrected** — the first verification used `grep -oE 'envoy\.filters\.http\.(lua|rbac)'` to full-text-match the whole waypoint config_dump, but what matched were entries in the Envoy bootstrap capability declaration list (`node.extensions`, alphabetically sorted), not the real filter-chain order — `lua` sorts before `rbac` alphabetically, coincidentally producing the plausible-but-wrong conclusion "Lua is before RBAC". Re-verifying against the real filter chain `inbound-vip|80|http|hello-backend.pr-lanes.svc.cluster.local`, the actual order is `rbac → grpc_stats → fault → cors → extensions.istio.io/trafficextension/pr-lanes.hello-backend-ratelimit → waypoint_upstream_peer_metadata → istio.stats → router` — **RBAC is before Lua rate limiting**, the opposite of the earlier record. This order is actually safer: unauthorized callers are already rejected by phase J's RBAC before reaching the rate limiter, so rate-limit quota isn't consumed by unauthorized traffic.
- **Rate-limit coverage boundary further clarified**: `targetRefs: kind: Service, name: hello-backend` only mounts the Lua filter on `hello-backend`'s own inbound filter chain for that VIP — covering traffic to the `hello-backend` VIP itself (including the portion internally forwarded to canary via the existing 90/10 `VirtualService` weight: measured via the waypoint's 429 counter showing both `destination_service_name=hello-backend` and `destination_service_name=hello-backend-canary` labels, ratio close to 90/10), but **not** covering traffic that directly calls `hello-backend-canary.pr-lanes.svc.cluster.local` (bypassing the `hello-backend` VIP split), nor the waypoint's `direct-http` chain — this is the second rate-limit-uncontrolled boundary after "bypassing the waypoint to hit a Pod directly".
- **The per-worker Lua state risk mentioned in the design doc's "Known limitations" did not materialize**: the waypoint's Envoy is `concurrency: 1` (single worker), so the token-bucket state is confirmed truly global, not the "≈2x approximation" risk the design doc originally worried about.
- **Phase J RBAC and phase K tracing/quota confirmed unaffected**: unauthorized calls still return 403, Telemetry tracing works, `pr-lanes-quota` stays at `requests 125m/320Mi`, `limits 500m/640Mi` unchanged.
