# K3s Phase F+G — Mesh-Driven PR Lanes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the cluster Istio Ambient (istiod + ztunnel + istio-cni + a per-Service waypoint) and rebuild the practice app `placeholder-hello` as a two-tier `hello-frontend` → `hello-backend` topology, so that an ArgoCD ApplicationSet PR Generator can spin up a per-PR "lane" that shares the frontend and the rest of the cluster, and only forks the one backend Service the PR touches — routed by an `x-pr-lane` HTTP header at the waypoint, not by namespace duplication.

**Architecture:** Cilium is reconfigured (`cni.exclusive: false`) to chain with `istio-cni`. Only the new `pr-lanes` namespace is labeled for ambient — every other namespace is untouched. `hello-backend`'s Service carries a waypoint; a static catch-all `HTTPRoute` sends unmatched traffic to the baseline backend, and one `HTTPRoute` per open (labeled) PR — generated by ArgoCD's `pullRequest` generator using `{{.head_sha}}` for the image tag and JSON6902 `patches` (not `nameSuffix`) for the per-lane resource names, to keep name propagation between the Service and its `HTTPRoute` backendRef unambiguous. CI gains a `pull_request` trigger that signs and pushes `hello-backend` tagged with the PR's head SHA. Two Kyverno policies get a namespace-scoped carve-out so PR-branch-signed images can pass admission inside `pr-lanes` only.

**Tech Stack:** Helm (`istio/base`, `istio/istiod`, `istio/cni`, `istio/ztunnel` @ `1.30.3`), Gateway API standard channel CRDs (`v1.6.1`), ArgoCD (existing, `ApplicationSet` `pullRequest.github` generator), Kyverno (existing, policy edits), GitHub Actions (existing pipeline pattern, new `pull_request` trigger), Sealed Secrets (existing, new GitHub PAT secret), `kubectl`, `istioctl`.

**Spec:** [docs/superpowers/specs/2026-08-18-k3s-phase-fg-mesh-pr-lanes-design.md](../specs/2026-08-18-k3s-phase-fg-mesh-pr-lanes-design.md)

**Depends on:** Phase B (ArgoCD + CI skeleton) and Phase E (Kyverno policies, all `Enforce`) — both complete. Independent of the same-day k3s→compose reversal (`docs/superpowers/plans/2026-08-18-k3s-to-compose-migration.md`); that plan touched `homepage`/`trilium`/`dify`/`evidence-os-website`, none of which this plan reads or writes.

## Global Constraints

- Pin image tags/digests. No `latest` (repo-wide rule, README.md). PR-lane images are pinned by commit SHA tag, which is immutable — this satisfies the rule even though the tag value is resolved dynamically by ArgoCD rather than hand-written.
- One change per commit, scoped to one compose/k8s stack (repo-wide rule). The Cilium change (Task 1) is its own commit, isolated from every other change in this plan — the spec calls this out explicitly as the highest-risk step.
- Istio charts: `istio/base`, `istio/istiod`, `istio/cni`, `istio/ztunnel`, all version `1.30.3`, repo `https://istio-release.storage.googleapis.com/charts`.
- Gateway API: standard channel, release `v1.6.1`, vendored into this repo (not fetched live by ArgoCD from the upstream release asset — this repo's convention is git as the sole source of truth).
- Namespaces: `istio-system` (new, `CreateNamespace=true`), `pr-lanes` (new, ambient-labeled).
- Mesh scope: **only** `pr-lanes` gets `istio.io/dataplane-mode=ambient`. No other namespace changes.
- Cilium: `cni.exclusive: false` added to `vps_oracle/k3s/cilium/values.yaml`; `bpf.masquerade` stays unset (must not be enabled — Istio's link-local health-check IPs break under it).
- Self-built images in scope for Kyverno's PR-lane carve-out: `ghcr.io/jeromefromcn/hello-backend` only. `hello-frontend` reuses the existing `ghcr.io/jeromefromcn/placeholder-hello` image/digest unchanged, no new image, no new Kyverno identity to account for.
- Repo path convention: `vps_oracle/k3s/istio/`, `vps_oracle/k3s/gateway-api/`, `vps_oracle/k3s/apps/hello/`, alongside `vps_oracle/k3s/argocd/apps/istio-{base,istiod,cni,ztunnel}.yaml`, `gateway-api.yaml`, `hello.yaml`, `pr-lanes-appset.yaml` — following the existing multi-source Helm `Application` pattern (see `kyverno.yaml`/`sealed-secrets.yaml`/`trivy-operator.yaml`).
- Label convention (from spec): `app: hello-frontend|hello-backend` (constant across baseline and every lane — this is what Kyverno's selector matches), `lane: baseline|pr-<N>` (distinguishes baseline from each lane; Service selectors match on `app` **and** `lane` together — matching on `app` alone would let the baseline Service pick up lane pods too).
- GitHub PR label (not a k8s label): `pr-lane` — a PR must carry this label before the ApplicationSet generates anything for it, and before the CI workflow's `pull_request` job builds anything for it.

### Task 1: Cilium `cni.exclusive: false`

**Files:**
- Modify: `vps_oracle/k3s/cilium/values.yaml`

**Interfaces:**
- Produces: a cluster where a chained CNI plugin (istio-cni, installed in Task 3) will not have its config file deleted by Cilium. Nothing downstream in this plan can work without this — Task 3's `istio-cni` DaemonSet would install cleanly but silently fail to redirect any traffic.

This is the plan's highest-risk step — it's a live change to the CNI underpinning every pod on this single-node cluster. It gets its own commit and its own verification pass before anything else in this plan touches the cluster.


Expected: no non-Running pods (baseline to compare against after the change); note the `free -h`/`top node` numbers for the before/after comparison in Task 14's resource log.

```yaml

# ... existing content above is unchanged ...

# Istio Ambient (phase F+G) chains istio-cni onto this node's CNI config.
# Cilium defaults to cni.exclusive=true, which actively deletes any other
```

- [ ] **Step 2: Sanity-check the download**

```bash

```

Expected: a count of at least 5 (standard channel currently ships `GatewayClass`, `Gateway`, `HTTPRoute`, `ReferenceGrant`, `BackendTLSPolicy` — count may be higher by v1.6.1, that's fine); the three greps each find a match.

- [ ] **Step 3: Write the ArgoCD Application**

```yaml
# vps_oracle/k3s/argocd/apps/gateway-api.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: gateway-api
  namespace: argocd
  annotations:
    argocd.argoproj.io/sync-wave: "-4"
spec:
  project: default
  source:
    repoURL: https://github.com/Jeromefromcn/docker-gitops.git
    targetRevision: main
    path: vps_oracle/k3s/gateway-api
  destination:
    server: https://kubernetes.default.svc
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - ServerSideApply=true
```

`ServerSideApply=true` because the upstream CRD manifest's annotations routinely exceed the `kubectl.kubernetes.io/last-applied-configuration` annotation's size limit under client-side apply — a known Gateway API CRD gotcha. `sync-wave: "-4"` puts it before Istio (Task 3 uses `-3` through `-1`), since `istiod` in ambient profile watches Gateway API resources on startup.

- [ ] **Step 1: Exclude `pr-lanes` from the existing main-branch-only policy**

```yaml
# vps_oracle/k3s/kyverno/policies/restrict-image-registry.yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: restrict-image-registry
spec:
  validationFailureAction: Enforce
  webhookTimeoutSeconds: 30
  rules:
    - name: verify-ghcr-jeromefromcn-signature
      match:
        any:
          - resources:
              kinds:
                - Pod
      exclude:
        any:
          - resources:
              namespaces:
                - pr-lanes
      verifyImages:
        - imageReferences:
            - "ghcr.io/jeromefromcn/*"
          # CI signs with cosign v3 keyless, which stores signatures as
          # Sigstore bundles in OCI referrers (no legacy sha256-<digest>.sig
          # tag). The default type "Cosign" only reads the legacy tag and
          # fails with "no signatures found".
          type: SigstoreBundle
          mutateDigest: false
          attestors:
            - entries:
                - keyless:
                    # keyless.subject is an exact match (no wildcards); use
                    # subjectRegExp to cover every repo workflow.
                    subjectRegExp: "^https://github\\.com/Jeromefromcn/docker-gitops/\\.github/workflows/[^/]+\\.yml@refs/heads/main$"
                    issuer: "https://token.actions.githubusercontent.com"
                    rekor:
                      url: https://rekor.sigstore.dev
```

```yaml
  name: restrict-image-registry-pr-lanes
spec:
  validationFailureAction: Enforce
  webhookTimeoutSeconds: 30
```

**Interfaces:**
- Produces: a Kustomize base the ApplicationSet (Task 12) points every generated `Application` at, with `images` + `patches` overrides supplying the PR-specific values. No `nameSuffix`/`commonLabels` transformers are used here — see the note below on why, since it directly affects how Task 12's patches must be targeted.

Every value that needs to vary per PR (names, the `lane` label, the header-match value, the image tag) is either a literal placeholder here (overwritten by an explicit `patches` `replace` op in Task 12) or an `images` override (a dedicated Kustomize transformer that matches on image repository name regardless of current tag — no ordering ambiguity with `patches`). This plan deliberately avoids `nameSuffix`: Kustomize's automatic reference-fixing (updating one resource's reference to another's *name* when that name changes) isn't guaranteed for Gateway API kinds like `HTTPRoute` the way it is for core Kubernetes types — betting the PR-lane's `backendRefs.name` on that would be a silent-failure risk (route stops matching, no error anywhere) that's cheap to avoid by just patching explicit literals instead.
