# lab-environment on k3s

Migrated from `~/jerome/lab-environment/docker-compose.yml` (a separate,
independently-managed project). Fully isolated `lab-environment`
namespace: no shared Prometheus/Grafana/alerting with `vps_oracle`'s own
monitoring stack (deliberate — this stack's `toxiproxy`-driven chaos
testing shouldn't share a pipeline with real incident alerting), no
cross-namespace scraping. (NPM does expose a few `*.lab.jerome.cloudns.asia`
hosts — api/consul/grafana/jaeger — behind an access list.)

## Runs always-on, on vps-oracle2

Since 2026-09-24 every Deployment runs on **vps-oracle2**, the k3s agent node
([`k3s/install/agent-vps-oracle2/`](../../install/agent-vps-oracle2/README.md)),
instead of sitting at 0 on vps_oracle to save its memory. Placement is not in
these manifests: the Kyverno mutate policy
[`lab-environment-on-oracle2`](../../kyverno/policies/lab-environment-on-oracle2.yaml)
injects `nodeSelector: dedicated=lab` and the matching toleration into every
Pod in this namespace. Monitoring: Grafana `Lab API Down` (end-to-end probe
through oracle2's NodePort) and `vps-oracle2 k3s Kubelet Down`.

This is a production-shaped environment, not a tidy one — replicas, mesh
policy, authorization, quotas and resilience values are all resident and are
meant to be demonstrated live (see the spec's implementation results). What is
deliberately *not* here is anything a real deployment wouldn't have.

**Replicas and rollout.** `customers-service` ×5 and `api-gateway` ×3 (real
load balancing, not one pod per service); everything else ×1 except the two
gateways (`waypoint` and `lab-ingress-istio` are generated by istiod with
×2 from their `parametersRef` ConfigMaps). The four business services use
`RollingUpdate` with `maxSurge: 1 / maxUnavailable: 0` and a PodDisruptionBudget,
so a rollout never drops below the replica count. A `lab.jerome/rollout-rev`
annotation on `customers-service` is the repeatable trigger for demonstrating
a rolling restart without changing the image.

The four Spring Boot services have a 1000m CPU limit (was 250m: startup took
61-98 s, half of it CFS-throttled; now ~40-55 s with all four starting at
once on the 2-core node) and startup + readiness probes on the actuator
`liveness`/`readiness` groups, so Ready means serving. If Consul isn't up yet
they exit 1 and retry — they settle on their own once it is.

**Quota.** `lab-environment-quota` caps **requests only** (`requests.cpu: 2`,
`requests.memory: 8Gi`); limits are deliberately uncapped, and each container's
own memory limit is its OOM ceiling. The 8Gi is derived, not arbitrary: ~70% of
the node's allocatable, and it covers a release peak — 5200 Mi steady state
plus one surge pod per rolling Deployment plus the `db-init` PreSync hook
(≈7.1 Gi). The previous 6Gi was the old `limits.memory` value carried over and
deadlocked a release on 2026-09-25 (the surge filled the quota, the hook was
refused with `FailedCreate`, and the sync stalled for 10 minutes). Note the
quota never binds on CPU — `requests.cpu: 2` equals the whole node, so the
node's own 2 cores do.

**Mesh.** The namespace is enrolled in Istio ambient (`istio.io/dataplane-mode:
ambient`), so every pod gets L4 mTLS from ztunnel with no sidecar. Services
that carry `istio.io/use-waypoint: waypoint` are routed through a 2-replica
waypoint Envoy, which is where L7 policy and telemetry live. External entry is
`lab-ingress-istio` (2 replicas, NodePort 30097) with an `HTTPRoute` to
`api-gateway`; `api-gateway` itself is ClusterIP and carries
`istio.io/ingress-use-waypoint: "true"`, without which ingress traffic bypasses
the waypoint and the edge policies never apply (verified).

**Identity and authorization.** Each business workload, the waypoint, Prometheus
and `db-init` have their own ServiceAccount, so policy is written against
principals rather than pod labels.

| Target | Allowed callers | Layer |
|---|---|---|
| customers-service | api-gateway | waypoint (L7) |
| visits-service | api-gateway, customers-service | waypoint (L7) |
| vets-service | api-gateway | waypoint (L7) |
| api-gateway | lab-ingress-istio | waypoint (L7) |
| any `/actuator/*` via waypoint | **denied** | waypoint (L7) |
| business pods, direct | waypoint SA; prometheus SA on the metrics port only | ztunnel (L4) |
| postgres | customers, vets, visits, db-init | ztunnel (L4) |
| redis | visits | ztunnel (L4) |
| ops UIs (grafana, jaeger, consul, prometheus, mcp-toolkit) | no policy — NPM reaches them in plaintext, an ALLOW policy would lock it out | — |

`PeerAuthentication` is STRICT for the four services, postgres and redis; the
ops UIs stay PERMISSIVE for the reason in the table. Kubelet probes are not
subject to either layer — measured, not assumed: pods stayed Ready throughout
the STRICT rollout, which would have rejected plaintext probe traffic had it
traversed ztunnel. The L7 policies were dry-run first (`istio.io/dry-run`) and
enforced only after a 15-minute window showed zero shadow denials on real
traffic and exactly one for a deliberate illegal call.

**Resilience (resident).** Per business Service, a `VirtualService` with
`timeout: 3s` and `retries {attempts: 2, perTryTimeout: 1s, retryOn:
connect-failure,refused-stream,unavailable,503}` for GET, and no retries with
`timeout: 5s` otherwise; the edge (`api-gateway`) never retries, so attempts
cannot multiply across hops. 500 is deliberately *not* retried. A
`DestinationRule` per service adds `outlierDetection {consecutive5xxErrors: 5,
interval: 10s, baseEjectionTime: 30s, maxEjectionPercent: 50}` and a generous
connection pool. With one replica (vets, visits) the 50% ejection floors to 0 —
Envoy never ejects the last healthy host, which is protection, not a fault.

Every workload carries `trivy-operator.skip: "true"` on its pod template: the
five `ops-lab/*` images can't be pulled for scanning, and nothing consumes the
namespace's reports.

## Service discovery and config

Two different jobs that used to be one:

- **Service discovery is Kubernetes-native.** The apps resolve each other by
  Service DNS (`petclinic.services.*-url` in each `application.yml`), which is
  what puts their calls through the waypoint where the mesh policy applies.
  The fork's Consul discovery starter and the gateway's `@LoadBalanced` /
  discovery-client wiring were removed for this. The toolkit's
  `get_service_health` reads EndpointSlices and pods, not Consul.
- **Consul is a config center and chaos-toggle store only.** The apps still
  read `config/<service>/data/*` through Spring Cloud Consul Config, and the
  fork's `ChaosToggleWatcher` polls `chaos/<service>/*` every 5 s. Nothing
  resolves addresses through Consul any more. The `chaos/` prefix is kept
  separate from `config/` on purpose: flipping a toggle must not trigger that
  library's app-wide config-refresh path.

The database password is **not** in either place. It lives in the
`lab-db-credentials` SealedSecret and reaches the pods as `DATA_DB_PASSWORD`;
the old plaintext value was rotated out and no longer authenticates (verify
over the scram path — `psql -h postgres` — because the same pod's local socket
matches a `trust` line in `pg_hba.conf` and will accept anything). To rotate:
update the secret, reseal, `ALTER USER`, then roll the three services.

## Schema

Schema and seed data are applied by a `db-init` PreSync Job
(`k8s/db-init.yaml`), not by the apps: the three services run
`SPRING_SQL_INIT_MODE=never`. The SQL is idempotent (`CREATE TABLE IF NOT
EXISTS`, `ON CONFLICT DO NOTHING`, and `setval(pg_get_serial_sequence(...))` so
sequences never rewind over rows the apps inserted). The Job, its
ServiceAccount and its SQL ConfigMap are all PreSync hooks at `sync-wave: -1`
— hook pods run *before* the same sync applies regular resources, so an
ordinary ServiceAccount/ConfigMap would not exist yet and the Job would fail
to create.

Test it without touching the cluster:

```bash
bash k3s/apps/lab-environment/tests/test-db-init.sh
```

That runs the SQL against a throwaway postgres container: legacy schema and
data first, then the Job twice, then an app insert, then the Job again —
asserting the seeds survive, app rows are not clobbered, and sequences do not
reset.

## After bringing it up: seed Consul KV (once)

`consul` runs as a `-server` with on-disk storage on a static local PV
(`consul-data`, see `k8s/pv.yaml`), so its KV survives restarts.
`server_rejoin_age_max` is raised (see `consul.yaml`): with the default 168h,
Consul refuses to start at all after a week offline. The old `-dev` in-memory mode
wiped `config/<service>/data/db.*` (and the chaos toggles) on every restart,
crash-looping `customers-service`/`vets-service`/`visits-service` with a
Hikari/JDBC placeholder error until the keys were re-put. Only seed once, on
first bring-up or after a manual KV reset:

```bash
CONSUL_HTTP_ADDR="http://localhost:30092" \
  bash ~/jerome/lab-environment/scripts/init-consul-kv.sh
```

`init-consul-kv.sh` no longer seeds `config/<service>/data/db.password` — the
password comes from the SealedSecret. It still seeds `db.host`, `redis.host`
and the `chaos/*` toggles (seeded to `false`).

Note: the PV is node-local on vps-oracle2 — the KV survives a node reboot but
not a node rebuild; re-seed after that.

## Host prerequisite: `fs.inotify.max_user_instances`

promtail tails every pod's log file individually (one inotify watch per
file, not per directory), and this node's default
(`fs.inotify.max_user_instances=128`) was already ~70/128 consumed by
everything else running as root on the box (containerd, cilium, other
pods) before this stack's 13 log files pushed it over the edge —
promtail crashed on startup with `too many open files` even though
`ulimit -n` itself was effectively unlimited (this is a separate,
unrelated kernel limit, not a per-container rlimit).

Raised to 1024 host-wide via `/etc/sysctl.d/99-inotify-instances.conf`
(persists across reboots) — on **vps-oracle2** now that the lab runs there
(vps_oracle keeps its own copy of the setting). This is a node-level setting,
not something expressible in a Pod spec — if the node is ever rebuilt, reapply:

```bash
ssh vps-oracle2 'echo "fs.inotify.max_user_instances = 1024" | sudo tee /etc/sysctl.d/99-inotify-instances.conf && sudo sysctl --system'
```

## NodePorts

Every NodePort answers on vps_oracle's `10.0.0.95` (NPM and the host relay
use this; Cilium forwards to oracle2 over VXLAN) and on vps-oracle2's
tailscale IP `100.100.140.33` (the blackbox probe uses this).

| Service | NodePort | Was (compose host port) |
|---|---|---|
| consul (UI/API) | 30092 | 8600 |
| prometheus | 30093 | 9190 |
| grafana | 30094 | 3100 |
| jaeger (UI) | 30095 | 16786 |
| mcp-toolkit | 30096 | 8865 |
| **lab-ingress-istio** | **30097** | 180 |

`30097` used to be `api-gateway`'s own Service; it is now the ingress gateway,
which fronts `api-gateway` (ClusterIP). The address is unchanged, so NPM's
`api.lab` host and the `Lab API Down` probe needed no edit — the probe's target
`http://100.100.140.33:30097/api/vet/vets` still means what it always did. The
handover is not atomic (two Services cannot hold one NodePort): it cost a
single ~4-second window where neither held it.

`postgres`, `redis`, `toxiproxy`, `loki`, `promtail`, `customers-service`,
`vets-service`, `visits-service` are ClusterIP-only, matching their
compose state (not published to the host there either). `api-gateway` joined
them with the ingress handover.

## Images

`mcp-toolkit`, `customers-service`, `vets-service`, `visits-service`, and
`api-gateway` are local-only builds with no registry behind them — containerd
can't pull them.

**Manifests reference immutable SHA tags** (`ops-lab/api-gateway:8839b4c7fa57`),
never `:dev`/`:latest`: a tag has to identify exactly one commit for a manifest
to mean anything, and it is what makes "roll back" a one-line change.
`build.sh` refuses to build from a dirty tree for the same reason, and tags
each image both `:dev` and `:<12-char git sha>`:

```bash
cd ~/jerome/lab-environment && ./scripts/build.sh        # prints FORK_TAG=… MCP_TAG=…
./scripts/push-to-k3s.sh ops-lab/customers-service:<sha> ops-lab/api-gateway:<sha> …
```

`push-to-k3s.sh` imports into **vps-oracle2's** k3s containerd (via `k3s ctr`,
not plain `ctr` — on oracle2 plain `ctr` is docker's, a different store) and
verifies the images landed. It refuses `:dev`/`:latest` outright.

If the source project rebuilds these images, re-run the import and restart
the affected Deployment, or containerd keeps serving the stale image it
already has (no pull happens for an image it believes it has).

**They are irreplaceable once deleted.** On 2026-09-24 they were found gone:
vps_oracle's `k3s-containerd-images` inspector check runs `crictl rmi
--prune`, and with the lab at `replicas: 0` nothing referenced them. The
oracle2 counterpart (`oracle2-k3s-containerd-images`) removes by ID and
always keeps `ops-lab/*`.

## Evidence

Everything below exists so a claim about the platform can be checked against
infrastructure output rather than the apps' own logs.

- **Traces.** Istio's `otel-lab` extension provider sends Envoy spans to this
  namespace's Jaeger over OTLP gRPC (`:4317`), and `Telemetry` sets tracing at
  100 % sampling. OpenTelemetry/W3C `traceparent` was chosen over Zipkin/B3
  deliberately: Spring Boot 4 propagates W3C, so B3 would split the app and
  Envoy spans into two traces. One external request therefore lands as a single
  trace spanning `lab-ingress-istio → waypoint → api-gateway → customers →
  visits`.
- **Access logs.** `lab-json-accesslog` writes Envoy's access log as JSON to
  stdout, including `trace_id`, `response_flags`, `attempts` and
  `upstream_host`. `response_flags` is where a timeout (`UT`) or a
  retry-limit (`URX`) becomes visible. Promtail parses the JSON and promotes
  only low-cardinality fields (`response_code`, `response_flags`) to Loki
  labels; `trace_id` stays in the line.
- **Log ↔ trace links.** Grafana's Loki datasource has a derived field on the
  32-hex trace id pointing at Jaeger, and the Jaeger datasource has
  `tracesToLogsV2` back to Loki. Both directions matter: a span is useless
  without its log line, and vice versa. Jaeger runs in-memory with
  `MEMORY_MAX_TRACES=5000`, so the link resolves for recent traffic only —
  roughly the last 1–1.5 h at the generator's rate.
- **Dashboard.** `Lab Mesh Overview` (uid `lab-mesh-overview`): per-pod RPS on
  customers-service, mesh requests by service and code, Envoy response flags,
  P99 by service, active outlier ejections, retry rate. Note the ejections
  panel reads "No data" until some cluster actually carries an outlier
  detection config — Envoy only materialises those stats once it does.
- **Traffic generator.** A small Deployment drives ≈1 rps through the ingress
  with a realistic mix (owners list, owner detail, vet list) and logs
  `timestamp code path`. It is the continuity check: after any change, its log
  should be all `200`.

## Rollback

Each implementation stage is independently revertible.

| Stage | Content | Rollback |
|---|---|---|
| 0 | PV backups; immutable image tags | — |
| 1 | `db-init` PreSync Job + `SPRING_SQL_INIT_MODE=never`; SealedSecret + password rotation, KV passwords removed | revert manifests; old password restorable via `ALTER USER` |
| 2 | Traffic generator; RollingUpdate + PDBs; Prometheus pod SD + RBAC; scale to ×5/×3 | scale back / revert |
| 3 | Fork discovery removal + toolkit K8s health | previous SHA tags |
| 4 | Ambient label, ServiceAccounts, waypoint, ingress gateway (30097 handover), OTel tracing, access logs, Envoy scraping, Grafana links + dashboard | remove the labels/Gateway, restore api-gateway's NodePort |
| 5 | PeerAuthentication, AuthorizationPolicy, VirtualService, DestinationRule | delete the CRs |
| 6 | Acceptance run, README | — |

Two orderings that matter if something goes wrong: deleting the waypoint (or
its `use-waypoint` labels) removes L7 enforcement *and* all edge telemetry at
once, so prefer reverting the individual policies; and the authorization
policies are enforced — if a legitimate caller starts getting 403s, re-add
`istio.io/dry-run: "true"` to that policy to restore the behaviour while you
find the missing principal.

## Data

`postgres` and `consul` are stateful, on static `local` PVs on vps-oracle2
(`k8s/pv.yaml`, `Retain`, `/var/lib/lab-environment/<name>`) — not
local-path, whose helper pod has no toleration for oracle2's taint. Both were
copied from their old vps_oracle local-path PVs on 2026-09-24 (backup:
`/home/ubuntu/backups/lab-environment-pv-2026-09-24.tar.gz` on vps_oracle).
Postgres was originally seeded from the compose
`lab-environment_postgres_data` volume. Everything else
(`prometheus`/`grafana`/`loki`) is ephemeral in the original compose
setup too — no data volumes there, so no PVC here either.

### Restoring data into a PV

The PVs are plain directories on vps-oracle2, so no seed Pod is needed
(that was a local-path `WaitForFirstConsumer` workaround). Stop the
workload by setting its `replicas: 0` in git (a bare `kubectl scale` is
reverted by selfHeal), then copy with ownership preserved — postgres data
is uid 999, consul uid 100:

```bash
sudo tar --numeric-owner -C <source-dir> -cf - . \
  | ssh vps-oracle2 'sudo tar --numeric-owner -xpf - -C /var/lib/lab-environment/<name>'
```

Restore `replicas: 1` in git afterwards.
